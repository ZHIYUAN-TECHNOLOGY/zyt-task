# ZYT commands

Copy-paste reference for the three zyt skills, the admin.zhiyuantech.ai site and their tests.
Paths are this machine's. `SETUP`, `UPDATE` and `AUDIT` below mean the skill folders:

```text
SETUP  = C:\Users\user\.claude\skills\zyt-setup
UPDATE = C:\Users\user\.claude\skills\zyt-update
AUDIT  = C:\Users\user\.claude\skills\zyt-audit
ZYT    = C:\Users\user\.claude\zyt          (registry pages.json, touch-log.jsonl)
```

Run `.ps1` scripts from PowerShell, not redirected from Git Bash.

## Which skill when

| Question | Skill | What it touches |
|---|---|---|
| "This app has no SOP page yet" | `/zyt-setup` | Writes a new `sop.json`, screenshots, builds, checks and publishes a new page |
| "Is the page still accurate?" | `/zyt-update` | Descriptive text (routes, labels, fields, step order, citations) follows the code; redeploys to the same URL after a yes |
| "Is the system itself right?" | `/zyt-audit` | Checks rules against every code path, hunts defects, re-verifies the ledger. Ledger ops only, never page text, never deploys |

Rules (`rules[]`) are business decisions: update and audit never rewrite a rule's text. Only `/zyt-update --rules` changes them.

## /zyt-setup

Three phases; each can be run on its own (a redeploy starts at phase 3).

```text
<project>/sop/<slug>/sop.json      single source of truth
<project>/sop/<slug>/shots/*.png   screenshots
<project>/sop/<slug>.html          built page
<project>/hosting/<worker-name>/   generated by publish.ps1
```

### Phase 1 — author

Discover the app, propose the chain (saved as `sop/<slug>/chain-proposal.md`) and wait for confirmation, then write `sop.json`.

Rules: propose, add `src` / `enforcement` / `ledgerId` from the code, show a tick list (max 15), apply only the ticked ids.

```bash
node UPDATE/scripts/rules.mjs propose --data <project>/sop/<slug>/sop.json --out <project>/sop/<slug>/.zyt/rules-candidates.json
node UPDATE/scripts/rules.mjs apply --data <project>/sop/<slug>/sop.json --candidates <project>/sop/<slug>/.zyt/rules-candidates.json --accept R1,R3
```

Roles (the "Show my flow" lens): propose, fill `unmapped` / `incomplete` steps, confirm once, apply.

```bash
node UPDATE/scripts/roles.mjs propose --data <project>/sop/<slug>/sop.json --out <scratch>/roles-proposed.json
node UPDATE/scripts/roles.mjs apply --data <project>/sop/<slug>/sop.json --candidates <scratch>/roles-proposed.json --accept all
```

`--allow-project` is needed for a `sop.json` under `C:\Project` (only with the user's yes in that run); `--allow-unmapped` lets steps without actors show under "All" only; `--dry` previews.

### Phase 2 — screenshots, build, check

```bash
node SETUP/scripts/capture-shots.mjs --plan shots.json --out <project>/sop/<slug>/shots --base http://localhost:PORT --playwright-from <dir>
node SETUP/scripts/build-page.mjs --data <project>/sop/<slug>/sop.json --out <project>/sop/<slug>.html
node SETUP/scripts/check-page.mjs --page <project>/sop/<slug>.html --out <project>/sop/<slug>/assets.json --screenshots <project>/sop/<slug>/review --guides 3,7 --playwright-from <dir>
```

- `capture-shots.mjs` only when the project has no usable capture tooling or screenshots.
- `build-page.mjs --no-ledger` leaves the fix list out; `--verified-at <iso> [--verified-commit <sha>]` prints the trust line.
- `check-page.mjs` fails on missing assets, console errors, overflow at 400px or localhost URLs. `--screenshots` saves review PNGs (read them), `--guides` also photographs those step guides, `--widths 1440,400` and `--allow-localhost` are optional.

### Phase 3 — publish (Cloudflare Worker)

```powershell
powershell -ExecutionPolicy Bypass -File SETUP/scripts/publish.ps1 -Source <project>/sop/<slug>.html -Name <worker-name> -AssetList <project>/sop/<slug>/assets.json -DryRun
```

Confirm account, worker name, public URL, ledger on/off and what the screenshots show, then run the same command without `-DryRun`. Afterwards take the baseline, or register a draft if it is not published yet:

```bash
node UPDATE/scripts/snapshot.mjs --page <id>
node UPDATE/scripts/registry.mjs add --sop-json <sop.json> --status draft
```

Worker names: `<client>-<slug>`, e.g. `jwa-full-chain-sop`.

## /zyt-update

| Invocation | Meaning |
|---|---|
| `/zyt-update` | Session mode: sync the pages this session's work affected |
| `/zyt-update --page <id>` | Session mode for one page |
| `/zyt-update --since-sync` | Scope = everything changed since the page's last sync, not just this session |
| `/zyt-update --all` | Sync-only check of every registered page; batched gates; deploy on yes |
| `/zyt-update --all ultracode` | Same, forcing the ultracode tier on every flagged page |
| `/zyt-update --status` | Report-only triage of all pages (no agents, no edits) |
| `/zyt-update --rules [--page <id>]` | Propose, tick and decide `rules[]`; dismiss `rule-at-risk` flags |
| `/zyt-update --roles [--page <id>]` | Propose and confirm `roles[]` and `steps[].actors` |
| `--no-deploy` | Stop after rebuild + check |
| `--install-hooks` | Show, and on a yes install, the edit-log and reminder hooks |

Two gates per run: GATE 1 (content that changes the process) and GATE 2 (before anything goes live).

### Underlying scripts

```bash
# scope and triage
node UPDATE/scripts/session-scope.mjs --cwd <cwd> --out <scratch>/sop-scope.json [--session <id>] [--since-sync]
node UPDATE/scripts/staleness.mjs --page <id> --json
node UPDATE/scripts/staleness.mjs --all --json --md <scratch>/triage.md

# draft and verify a changeset
node UPDATE/scripts/reanchor.mjs --page <id> [--out <changeset>]
node UPDATE/scripts/evidence-verify.mjs --changeset <p> --code-root <root> --out <p>

# apply (--accept auto | all | explicit op ids; --source session | all-light | all-ultracode | audit | rules | roles)
node UPDATE/scripts/sop-patch.mjs --data <sop.json> --changeset <p> --source session --accept auto,op-003 --check-old [--dry]

# rules (source rules: the only way a rule changes)
node UPDATE/scripts/rules.mjs propose --page <id>
node UPDATE/scripts/rules.mjs apply --page <id> --candidates <rules-candidates.json> --accept R3,R10 [--dry] [--allow-incomplete]
node UPDATE/scripts/rules.mjs list --page <id>
node UPDATE/scripts/rules.mjs dismiss --page <id> --rule R10 --note "<the user's reason>"

# registry
node UPDATE/scripts/registry.mjs list
node UPDATE/scripts/registry.mjs get --id <id>
node UPDATE/scripts/registry.mjs discover --roots C:\Project --dry
node UPDATE/scripts/registry.mjs set --id <id> --key verifiedAt --value "\"2026-09-16T00:00:00Z\""
node UPDATE/scripts/registry.mjs record --id <id> --synced-at <ISO> --synced-scope 11,12

# baseline and publish
node UPDATE/scripts/snapshot.mjs --page <id>
powershell -ExecutionPolicy Bypass -File UPDATE/scripts/publish-page.ps1 -Page <id> -DryRun -PlaywrightFrom <dir>
```

Session runs record only `lastSyncedAt` / `lastSyncedScope`. `verifiedAt`, `verifiedCommit` and `verifiedBy` are set only by a full-page `--all` run with `coverage.full: true`. `publish-page.ps1` refuses a `site-script` publisher (such as the NCT page) unless `-DryRun` or `-ConfirmSiteScript`.

## /zyt-audit

| Invocation | Meaning |
|---|---|
| `/zyt-audit --page <id>` | Ultracode audit of one page (default) |
| `/zyt-audit --page <id> --light` | Rule checkers, one pattern hunter, one ledger checker, one refuter |
| `/zyt-audit --all-pages` | Every registered page, filtered by `ZYT_ALLOW_PAGES` |
| `--budget <agents>` | Maximum agents for the run (default 25) |

`--page` is required unless `--all-pages` is given.

### GATE 0 — plan, then ask

```bash
node AUDIT/scripts/audit-plan.mjs --page <id> [--light] [--budget 25] --today 2026-09-16
```

Prints agents per role, token range, output paths and whether it fits the budget (exit 3 when over). Nothing fans out without a yes.

### Run the workflow

```bash
node AUDIT/scripts/audit-plan.mjs --page <id> [--light] [--budget 25] --today 2026-09-16 --json --out <scratch>/audit-args.json
```

Then `Workflow({ scriptPath: "AUDIT/workflows/zyt-audit.js", args: <contents of audit-args.json> })`. It writes `<sopDir>\.zyt\audit-<date>.json` and `audit-<date>.md`, and dry-runs sop-patch.

### Record, then apply by id

```bash
node UPDATE/scripts/registry.mjs record --id <id> --audited-at <ISO>
```

```powershell
powershell -File AUDIT/scripts/audit-apply.ps1 -Page <id> -Accept auto,op-002,op-005 [-Date 2026-09-16] [-Dry]
```

`-Accept` takes `auto` and explicit `op-NNN` ids only; `all` is refused. Legacy pages are report-only. The audit never deploys and never runs the app, Convex or tests.

## Golden paths (e2e you can watch)

A *golden path* is one SOP journey as a Playwright test, written so a person can follow it play by
play. A runbook step on the dashboard carries a **▶ Run golden path** button: pressing it starts a
headed, slowed-down run **on your own computer**, streams each step into the panel, and shows the
recording when it finishes.

Start the runner first — the page cannot reach your machine without it:

```bash
node C:/Project/ZYT-Task/hosting/runner/server.mjs
```

Then open the step and press the button:

| Runbook step | Journey | Job id |
|---|---|---|
| `rb-nct-b3-merge-wave-1` | SOP steps 1–3 · enquiry → customer → primary contact | `nct-intake-steps-1-3` |
| `rb-nct-c3-gates-04-05` | SOP steps 4–7 · quotation → containers → rate card → tariff floor | `nct-quote-build-steps-4-7` |
| `rb-nct-c5-drift-count-08` | SOP steps 8–10 · submit → approve → freeze → send screen → decide | `nct-quote-decide-steps-8-10` |

```text
https://admin.zhiyuantech.ai/?company=nct&task=rb-nct-b3-merge-wave-1
```

- The runner listens on `127.0.0.1` only and answers `https://admin.zhiyuantech.ai` alone, so a
  visitor's click can only ever reach **their own** machine. One run at a time.
- Each run seeds its own throwaway organization on the **dev** database and deletes it afterwards;
  the suite refuses to run against production.
- **Chrome or Edge only.** Safari blocks a public page from reaching `127.0.0.1`, and so does the
  Claude desktop app's built-in browser.
- Specs live in `C:/Project/NCT/nct-layout/e2e/specs/*.golden-path.spec.ts`; recordings land under
  `e2e/out/<feature>/<slug>/`. Jobs are the `JOBS` map in `hosting/runner/server.mjs`.

### Writing another one

In a session opened on `C:/Project/NCT/nct-layout`:

```text
Read e2e/README.md "Adding a golden path" and e2e/specs/quote-build.golden-path.spec.ts, then
write the same kind of journey for SOP step <n>. The SOP text is in
C:/Project/ZYT-Task/customer-intake-sop/sop.json (steps array, entry n=<n>). Write it against the
app as it works TODAY, and prove it with --project <name> before wiring any button.
```

Run it headless before wiring anything (both secrets come from `apps/server/.env`):

```bash
cd C:/Project/NCT/nct-layout && npx playwright test --config e2e/playwright.config.ts --project <name>
```

To give it a button: add a `JOBS` entry in `hosting/runner/server.mjs` (no deploy needed), then
`"run": "<job id>"` on a step in `tracker/seed/runbook-nct.json` and redeploy the site.

Three rules, each learned the hard way:

- **Write it against today's behaviour, never against a plan.** A golden path that asserts a
  planned fix is a red suite people learn to ignore. Two steps deliberately assert defects — an
  applied rate line ignores the containers' quantity, and a decision cannot be corrected.
- **Never press Send on a quotation.** Sending goes through a real connected mailbox: there is no
  dev transport and no outbox, so a live Gmail in the dev database would mail a real customer. The
  steps 8–10 journey opens the send dialog and cancels.
- **Give every spec a project** in `e2e/playwright.config.ts`. A spec matching no project is
  silently never run, and it looks like coverage.
