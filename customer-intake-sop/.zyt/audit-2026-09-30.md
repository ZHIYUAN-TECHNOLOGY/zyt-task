## New defects

### op-001 - confirm - pattern unenforced-approval - step 18
**Holding only 'Correct extraction' is enough to approve a carrier MBL/HBL** (sev data)

Step 18 says approving a document needs its own review right (document.review.approve). The Approve button calls review.approve, which checks that permission. But "Save corrections & approve" and a document-type change both call review.correct, which only checks document.review.correct. That endpoint then finalises the document as approved: persistFinal writes a final extraction, sets the status to approved and stamps reviewedBy. It also runs the approval hooks that start the B/L tracking job. A role given "Correct extraction" without "Approve extraction" can edit one field, or only change the type, and approve the MBL/HBL that way. The permission tree lists these as two separate powers, so an admin who splits them still gets the approval the split was meant to block.

### op-002 - confirm - pattern handoff-drop - steps 18-19
**An auto-approved B/L whose tracking job fails or is refused tells nobody** (sev data)

When an organisation sets a document type to auto_approve, the extraction workflow approves the MBL/HBL by itself. It then runs the approval hooks, which create the bl_job that the demurrage board reads. runApprovalHooks catches any hook failure and returns it as an `approval_hook_failed` notice, together with any re-sync the automation refused. The workflow discards that return value. On the reviewer path these notices are shown to a person. On the automatic path nothing is recorded, nobody is notified and no task is created. The document shows as approved but has no tracking job, so the 72h demurrage clock is never watched and nobody knows it is missing. The workflow's own comment says a swallowed failure means no tracking job. The default policy is review_all, so this only affects organisations that opt in.

Evidence:
